# 名刺管理(仮称)— SPEC

slug: `bizcard` ／ 作業の前に `CLAUDE.md` と `core/README.md` を読むこと。

## 概要

- 一言: 名刺の写真を取り込むと連絡先データベースになり、「この人、誰だっけ」を思い出せる記録を残せる。名刺は端末の外に出ない。
- 対象: 名刺を多く受け取る個人事業主・フリーランス・営業職の人。
- 注意書き(アプリとLPに必ず載せる): 読み取り結果は確認が前提です。相手の情報をアプリが自動で集めることはありません。
- 対応OS: macOS(Apple Silicon)・Windows(x64)。最低ライン: Core i5-12500級・メモリ16GB・GPUなし。
- 販売: 外部の販売プラットフォーム(買い切り)。決済・税・キー発行は自作しない。
- **競合に注意**: 既存の名刺管理アプリ(クラウド型を含む)は多い。差別化は「他人の個人情報を端末の外に出さない」「買い切り」「『誰だっけ』の記録が中心」。競合調査は本スペックの外で別に行う(未実施)。

## 最重要の設計方針(「この人、誰だっけ」)

名刺は、受け取った直後は覚えていても、数週間後に「この人、誰だっけ」となる。このアプリの価値は読み取りの精度より、**あとで思い出せる記録**にある。

- 取り込んだ直後に、「会った日・場所・きっかけ・話した内容」をすばやく残せる入力欄を出す(スキップできる)。
- 検索結果と詳細画面には、**名刺の画像と、自分のメモを大きく**表示する。
- 1つの検索窓で、氏名・会社・役職・メモ・タグ・場所のすべてを探せる。
- 相手のSNS・公開情報は、**アプリが自動で集めない**。利用者がメモ欄に自分で書く、またはコピペして残す。アプリは外部サイトを検索・取得しない。

## ユーザーの流れ

基本は**カメラで名刺を撮影**する。ここでの「カメラ」は、PCのウェブカメラ(`getUserMedia`)。カメラが使えない・手元に写真があるときは、写真ファイル(JPEG / PNG / PDF)やフォルダの取り込みを併用する。

1. 撮影画面。上にカメラのプレビュー、撮影ボタン。カメラが使えなければ、取り込みだけを出す。
2. 撮影すると、その場で名刺の画像が表示され、**画面の下部に読み取り結果の枠(項目ごと)**が出る。氏名・ふりがな・会社・部署・役職・メール・電話・携帯・郵便番号・住所・URL。信頼度が低い項目に「要確認」の印。
3. 各項目は、その場で**打ち替え(修正)**できる。元に戻す(直前の打ち替えを取り消す)、項目ごとに読み取り結果へ戻す、やり直し(下書きを捨てて撮り直す)ができる。
4. 同じ画面で「会った日・場所・きっかけ・メモ」を残せる(空欄のまま確定できる)。確定を押して初めて連絡先として保存される。
5. **連続撮影**: 確認を待たずに続けて撮れる。撮った名刺は上部のキューに並び、1枚ずつ確認・確定する。
6. 検索窓で探す。「誰だっけ」と思ったら、検索して画像とメモを大きく見る。必要なときにCSVで書き出す。

画面は**最初から縦持ちの狭い幅(スマホ幅)でも使える**レスポンシブにする(タップしやすい大きさ、下部に固定した確認枠、背面カメラ優先)。ただし、スマホ向けのアプリとOCRは今回作らない(下の「見送り」「要確認」)。

## スコープ(2週間で出す範囲)

- [ ] 取り込み: **カメラ撮影(PCのウェブカメラ)**、JPEG / PNG / PDF、フォルダ。1人につき表・裏の複数画像を紐づけられる。失敗したファイルは飛ばして続行。同一画像(SHA-256)の重複は取り込まない
- [ ] OCR(`core` の `ocr`)で、氏名、ふりがな(あれば)、会社、部署、役職、メール、電話、携帯、郵便番号、住所、URL を読み取る
- [ ] (ロジックとテスト・実OCR測定まで実装済み。取り込み画面は未実装。`src-tauri/src/extract.rs`) ルール抽出: メール・電話・郵便番号・URL は正規表現。会社は「株式会社」「有限会社」「合同会社」「Inc.」等の語。役職は語彙(部長・課長・代表取締役 等)。氏名は、文字の大きさと位置(OCRの位置情報)と語彙から候補を出す。日本語と英語の名刺の両方に対応。**生成モデルは使わない**(初版)
- [ ] 確認画面(`core/ui`): 撮影した画像を表示し、**画面の下部に項目ごとの枠**を出す。項目ごとに打ち替え、信頼度が低い項目に印、一括確定、元に戻す、やり直し、連続撮影のキュー。確定するまで連絡先として保存されない(画面は `ui/` にモックのAPIで実装済み。Tauri 接続は未検証。`docs/ui/` にスクリーンショット)
- [ ] (ロジックとテストのみ実装済み。画面は未実装。`src-tauri/src/dedup.rs`) 重複の検知: メールが同じ、または氏名と会社が同じ人を「同じ人かもしれません」と提示し、統合するかを確認する(自動で統合しない)
- [ ] (保存・履歴・検索のロジックとテストのみ実装済み。`src-tauri/src/store.rs`。画面は未実装) 「誰だっけ」の記録: 会った日、場所、きっかけ、メモ、タグ。**メモは複数追加でき、日付つきの履歴**になる(再会したときに追記)
- [ ] (ロジックとテストのみ実装済み。3文字未満・2文字氏名「田中」はLIKEで当たる。画面は未実装) 一覧と検索(SQLite FTS5)。最近追加した順、会った日の順、会社別、タグ別
- [ ] (CSV と vCard 3.0 のロジックとテストのみ実装済み。`csv_export.rs` `vcard.rs`。画面は未実装) 書き出し: CSV(UTF-8 BOM付き / Shift_JIS の選択、セルの無害化)。vCard 3.0 は余力があれば
- [ ] 設定: 通信一覧の表示、更新確認のオン/オフ、データの全削除、ライセンスの有効化
- [ ] 進捗・中断・再開(`core/jobs`)

## データモデル(SQLite)

```
people(id, name, name_kana, company, department, title, email, phone, mobile, postal_code, address, url,
       status, field_confidence_json, created_at, updated_at)
  -- status: 'draft' | 'confirmed'
card_images(id, person_id, side, sha256 UNIQUE, stored_path, imported_at)
encounters(id, person_id, met_on, place, how_met, memo, created_at)  -- 会った日・場所・きっかけ・メモ(履歴)
tags(id, name UNIQUE), person_tags(person_id, tag_id)
people_fts(name, name_kana, company, department, title, memo_all, place_all, tags_all)  -- FTS5(trigram を試す)
jobs(id, kind, state, progress, error, payload_json)
```

- 画像はアプリのデータフォルダにコピーして保持する(元のファイルは上書きしない)。
- 個人情報なので、ログに氏名・メール・電話を書かない。

## スパイク(最初の2日。合格しなければ止まって報告)

テストセット: 名刺 50枚(**架空の名刺を自作**する。実在の他人の名刺をテストに使う場合は個人情報をマスクする)。横書き・縦書き・英語・装飾フォント・斜め撮影・裏面(英語表記)を混ぜる。正解の項目を人が付けて `testset/` に置く。

| 指標 | 合格ライン(提案値・未検証) |
|---|---|
| 名刺1枚(OCRから抽出まで) | 3秒以内(最低ライン相当) |
| メール・電話の正答率 | 95%以上 |
| 会社名・氏名の正答率 | 85%以上(確認画面で直せる前提で、まず測る) |
| ピークメモリ | 4GB以内 |
| インストール容量 | 2GB以内を目安 |

- 測定は、GPUを使わない設定・スレッド数6〜12で行う。Mac(Apple Silicon)は基準にしない。
- 合格しない場合は、(a) ルールの拡充、(b) 別のOCR、(c) 機能の縮小(氏名と会社は手入力を主にする等)、の順に提案して**止まる**。

## データの保存と削除

- 保存場所: OSのアプリデータフォルダ内の、アプリ専用フォルダ(名刺画像のコピー、SQLite、ログ)。
- 削除: 1人ずつ(画像・メモを含めて)削除できる。設定の「全データを削除」で全部消える。
- 暗号化: 初版はアプリ内の暗号化を行わない。OS のディスク暗号化(BitLocker / FileVault)の案内を設定画面に載せる。SQLCipher の採用は「要確認」。**他人の個人情報を扱うため、この判断は発売前に必ず行う。**
- 書き出し(CSV)は、利用者が自分で管理する。書き出し時に「個人情報を含むファイルです」と表示する。

## 要確認(あなたの判断が必要なこと)

- (止まったときは、ここに質問を1行で書く)
- **スマホで撮影する案(検討事項。確定ではない)**: 実現するにはスコープ変更(CLAUDE.md の「スマホ向けの実装は作らない」の見直し)になる。論点: ①端末内OCR — ONNX Runtime のモバイル対応と、PP-OCR の速度・メモリ・容量は未検証。②Tauri 2 の iOS / Android 対応は未検証。③配布と審査 — App Store / Google Play の規約・審査・手数料・署名は未確認で、「外部の販売プラットフォームで買い切り」と両立するか不明。④競合は既にスマホアプリ中心(Eight、CamCard 等。`/docs/research/bizcard.md`)で、差別化(端末の外に出さない)がスマホ上でも成り立つかの確認が先。当面は、PCのウェブカメラと写真取り込みで進める
- (解消) core に `ocr` / `db` / 汎用 `write_csv` が入ったため、`ocr_input.rs` は core::ocr の型の再公開に、CSV は core の `write_csv` に置き換えた。
- **スパイクの精度が合格ライン未達**(合成画像50枚・実OCR): メール・電話・携帯・FAXが1枚で全部一致 76%、会社 50%、氏名 80%(`docs/spike-results.md`)。SPEC.md の手順に従い、(a)ルール拡充 / (b)別のOCRやモデル / (c)機能縮小(氏名・会社は手入力主体) のどれで進めるか、判断したい。ここで止める
- **縦書きが読めない**(縦書き8枚で氏名・会社・役職が 0): `core::ocr::ppocr` の縦書き処理(領域を水平に回して読む)が原因と推測。`core/` は変更しないため、receipt-db 側(core の持ち主)に、縦書き領域を1文字ずつ切り出して横に並べる処理を依頼してよいか確認したい
- **日本語認識モデルの出所が未確認**(`docs/licenses.md`): 製品に同梱できない。公式配布元からの取得とハッシュ照合ができる環境で確認が必要。確認できなければ、日本語の名刺を読む方式の再検討になる
- 画像のテストセットは合成(25レイアウト×2)。実際の名刺(個人情報を伏せたもの)20〜30枚があれば再測定したい
- **people.email が1つだけ**: SPEC.md のデータモデルは `email` 1列だが、名刺には複数のメールが載ることがある(架空セットの15番)。複数メール用の表を足すのはスコープの変更に当たるため、先頭を `email`、残りをメモに入れる運用でよいか確認したい
- 依存ライセンスの配布時の表記(`docs/licenses.md`)は、LICENSEファイルの中身を未確認
- 参考: 競合調査は `docs/research/bizcard.md` ではなくリポジトリ直下の `/docs/research/bizcard.md` にある(このアプリのフォルダ内には無い)
- 初期の論点: SQLCipher を初版に入れるか(推奨: 入れず、全削除とディスク暗号化の案内で始める。発売前に再判断)、vCard を初版に入れるか、HEIC の扱い
