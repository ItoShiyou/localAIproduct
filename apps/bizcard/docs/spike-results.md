## 2. ルール抽出の、架空データでの結果

### 条件

- 対象: `testset/cards/` の架空の25枚(OCR出力を手で模したJSON。**実画像でも実OCRでもない**)。内訳は `testset/README.md`
- 実行: `cd src-tauri && cargo run --example eval`(採点は `src/eval.rs`)。`cargo test` で結果を固定している
- 環境: Linux のクラウド環境(4 vCPU)。Mac / Windows、基準機は未使用
- 採点: 項目ごとに、空白と全角半角の違いを除いて、正解ラベルと完全一致なら正解。複数値の項目(メール等)は集合として一致
- **ルールは、このテストセットを見ながら書き、正解ラベルも同じ作業者が付けた。** よって、ここでの正答率は「想定した形にルールが合っているか」を示すだけで、実際の名刺での精度の予測にはならない。SPEC.md の合格ラインとの比較にも使えない

### 結果(25枚)

| 項目 | 一致 / 25 |
|---|---|
| 氏名 | 24 |
| ふりがな | 25 |
| 会社 | 23 |
| 部署 | 25 |
| 役職 | 25 |
| メール | 23 |
| 電話 | 23 |
| 携帯 | 24 |
| FAX | 25 |
| 郵便番号 | 25 |
| 住所 | 25 |
| URL | 25 |
| メール・電話・携帯・FAXがすべて一致(1枚単位) | 21 |

内訳: 「想定内」の13枚は全項目が一致。「難しい」12枚(意図的に想定外の形を混ぜたもの)のうち、7枚で次の不一致が出ている。

| 名刺 | 外れた項目 | 原因(想定したもの) |
|---|---|---|
| 12 | メール | OCRが `.` を `,` に誤認識した想定。ルールでは直さない |
| 19 | 会社 | 会社名に「株式会社」「Inc.」等の語がない |
| 21 | 氏名 | カタカナの外国人名(中黒入り)を氏名の形として扱っていない |
| 22 | 電話・携帯 | ハイフンのない電話番号を拾っていない |
| 23 | メール | OCRが `@` の前後に空白を入れた想定 |
| 24 | 会社 | 会社名が2行に折り返された想定(1行ずつしか見ない) |
| 25 | 電話 | 縦書きでOCRが文字ごとに空白を入れた想定 |

これらは**直していない**(限界の記録として固定している。`src-tauri/tests/testset.rs`)。次の手は SPEC.md の順(a)ルールの拡充(ハイフンなしの電話、空白の混入の除去、カタカナ名、2行会社名)。ただし、実OCRの出力を見てから優先順位を決めるべきで、いま架空データに合わせて足すのは過学習になる。

### 速度(ルール抽出のみ・OCRを含まない)

- release ビルド、25枚を200回繰り返した平均で、1枚あたり約 0.009 ms(4 vCPU の Linux クラウド環境、単一スレッド)。
- これはルール抽出だけの時間。「OCRから抽出まで3秒」の判定には使えない(OCRが未測定)。基準機の値でもない。
