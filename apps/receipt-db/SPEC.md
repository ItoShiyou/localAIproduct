# 領収書DB(仮称)— SPEC

slug: `receipt-db` ／ 作業の前に `CLAUDE.md` と `core/README.md` を読むこと。

## 概要

- 一言: 領収書や請求書のPDF・画像を取り込むと、日付・金額・支払先などを読み取って、検索できるデータベースに保存する。ファイルは端末の外に出ない。
- 対象: 個人事業主・副業の方。領収書をクラウドのAIに貼って整理していた人。
- 注意書き(アプリとLPに必ず載せる): 読み取り結果は確認が前提です。税務上の判断や申告の責任は利用者にあります。手書きの書類は対象外です。
- 対応OS: macOS(Apple Silicon)・Windows(x64)。最低ライン: Core i5-12500級・メモリ16GB・GPUなし。
- 販売: 外部の販売プラットフォーム(買い切り)。決済・税・キー発行は自作しない。

## ユーザーの流れ

1. 領収書(PDF・画像)をドラッグして取り込む(複数可、フォルダ可)。
2. 読み取りが進む(進捗表示。閉じても続く)。
3. 確認画面で、原本の画像と読み取り結果を並べて見て、直して「確定」。
4. 一覧と検索で探す。必要なときにCSVで書き出す。

## スコープ(2週間で出す範囲)

- [~] 取り込み: PDF、JPEG/PNG、フォルダ。失敗したファイルは飛ばして続行し、結果に失敗理由を表示。同一ファイル(SHA-256)の重複は取り込まない
- [~] PDFにテキスト層があれば直接読む。なければ画像にして OCR(`core` の `ocr`)
- [x] ルール抽出(`rules.rs`): 日付(西暦・和暦)、税込合計、税率(10% / 8% / 混在なら空欄)、登録番号(T+13桁)
- [~] 支払先・摘要: まずルール(先頭付近の会社名らしい行、「株式会社」「有限会社」などの語)で候補を出す。生成モデルは**使わない**(初版)
- [~] 確認画面(`core/ui`): 原本と並べて表示、項目ごとに修正、信頼度が低い項目に印、一括確定、元に戻す。**確定するまでデータベースの「確定済み」にならない**
- [x] データベース(SQLite): 一覧、日付・金額・支払先での検索(全文検索)、編集、削除(原本のコピーも消す)
- [x] 勘定科目の候補(ルールと辞書。支払先のキーワードから。自動確定はしない)
- [x] 書き出し: CSV(UTF-8 BOM付き / Shift_JIS の選択、セルの無害化)、SQLiteファイル
- [~] 設定: 通信一覧の表示、更新確認のオン/オフ、データの全削除、ライセンスの有効化
- [x] 進捗・中断・再開(`core/jobs`)

凡例: `[x]` = Rust ロジックを実装し `cargo test` で検証済み、`[~]` = 一部のみ(下の注)。
**2026-10-04(Mac M2)**: Tauri 2 + React の画面を接続し、`tauri dev` で起動を確認(`docs/ui/mac-launch.png`)。取り込み(ファイル・フォルダ・ドラッグ&ドロップ)→ 読み取りの進捗・中断・再開 → 確認画面(原本と並列、要確認の印、指摘があると確定不可、元に戻す、一括確定)→ 一覧・検索・削除 → CSV/SQLite 書き出し(保存ダイアログ)→ 設定(通信一覧、更新確認のオン/オフ、全削除)。画面の流れはモックAPIで Playwright により確認(`ui/e2e/flow.mjs`、`docs/ui/mock-*.png`)、実OCRでのコマンド経路は `src-tauri/tests/real_ocr_flow.rs` で確認。**実アプリ上での手操作の通し確認と Windows ビルドは未実施。**
- 取り込み: ロジック済み(重複・失敗の継続・原本コピー)。ドラッグ&ドロップの画面は未着手。
- PDF/OCR: テキスト層と、埋め込みJPEGのスキャンPDFは検証済み。JPEG以外の画像PDFは非対応。`PpOcr` を実際のモデルでつなぐ結合(モデル同梱・onnxruntime の読み込み設定)は未実施。
- 支払先: ルール済み。摘要の候補は未実装(空欄、確認画面で入力)。
- 確認画面: 下書き/確定、修正、元に戻す、一括確定、信頼度(`low_confidence_fields`)のロジックまで。画面(原本との並列表示)は未着手。
- 設定: 通信一覧・更新確認の停止・全データ削除のロジックまで。ライセンスの有効化は実接続なし(トレイトのみ)。

## データモデル(SQLite)

```
documents(id, sha256 UNIQUE, original_name, stored_path, kind, imported_at)
receipts(id, document_id, page, date, vendor, total, tax_rate, invoice_no, summary,
         account_candidate, status, field_confidence_json, created_at, updated_at)
  -- status: 'draft' | 'confirmed'
receipts_fts(vendor, summary, invoice_no)  -- FTS5。日本語の部分一致は trigram を試す
jobs(id, kind, state, progress, error, payload_json)
```

- 原本は、アプリのデータフォルダにコピーして保持する(元のファイルは上書きしない)。
- 金額は整数(円)。日付は `YYYY-MM-DD`。実在しない日付は保存せず、確認画面で指摘する。

## 技術選定(初期案)

| 部品 | 初期案 | 確認すること |
|---|---|---|
| 殻 | Tauri 2 + React + TypeScript + Vite | Mac / Windows の両方でビルドできる |
| PDF | テキスト層の取得とページの画像化(PDFium 系などを比較) | 日本語PDFのテキスト層の取得精度、ライセンス |
| OCR | OS標準(Windows / macOS)と、ONNX Runtime 上の軽量OCRを比較 | 日本語の精度、1ページの秒数、モデルの容量、ライセンス |
| 検索 | SQLite FTS5(trigram) | 日本語の部分一致が使える |

### 技術選定の結果(スパイク 2026-10-03。詳細と数値は `docs/spike-results.md`、ライセンスは `docs/licenses.md`)

注意: 測定は Linux の 4 vCPU 仮想マシンと**架空の合成データ50件**だけ。Mac・Windows・最低ライン機・実際の領収書は**未実測**。

| 部品 | 選定(案) | 理由 | 未確認 |
|---|---|---|---|
| 殻 | Tauri 2 + React + TypeScript + Vite のまま。ただし `src-tauri/` は今は Tauri なしの Rust クレート(`cargo test` で検証できるロジックを先に作る) | Linux では画面をビルドできない | Mac / Windows でのビルド(未実測) |
| PDFのテキスト層 | `pdf-extract`(MIT)。テキスト層ありPDF 15件が PyMuPDF と全件一致、0.002秒/ページ | PyMuPDF は AGPL で製品に使えない | 複数ページ、実際の請求書PDF |
| 画像のみのPDF | 第一案: PDFium(`pdfium-render`)で画像化。第二案: `lopdf` で埋め込みJPEGを取り出す | PDFium の取得が通信制限で未実施 | 両方未実測 |
| OCR | **ONNX Runtime 上の PP-OCR を自作実装(`core::ocr::ppocr`)。検出 v4 + 認識2つ(日本語 v3 と中国語 v4)を併用**。Tesseract は予備(`core::ocr::tesseract`) | OSごとのコードが要らない。合成データで数字 50/50、支払先 48/50。約55MB、ピーク約1.2GB、1枚 約0.6〜1秒(この環境) | OS標準OCRとの比較、最低ライン機での時間、実データの精度、日本語モデルの出所(要確認) |
| 抽出 | ルール(`rules.rs`、`vendor.rs`)。生成モデルは使わない | 数字の項目はルールで足りた | 実データでの精度。ルールを同じ50件で調整したので楽観的 |
| 検索 | SQLite FTS5 trigram + 3文字未満の語は LIKE(`core::db`)、NFKC でそろえる | 2文字の語(「書店」)が trigram で 0 件になるのを実測 | Mac / Windows での SQLite 動作 |

OCR方式の比較(要約。表は `docs/spike-results.md`): Tesseract 単独は数字が弱い(金額 35/50)。中国語の認識モデルだけだと仮名を落とし(支払先 15/50)、日本語の認識モデルだけだと「T」「¥」を読み違える(登録番号 27/50)。**2つで読んで使い分ける**と、両方が合格ラインに届いた(合成データ)。

## スパイク(最初の2〜3日。合格しなければ止まって報告)

テストセット: 領収書・請求書 50件(個人情報は伏せるか、架空のデータで作る)。レシート(感熱紙の薄れ・斜め撮影を含む)、請求書PDF(テキスト層あり/なし)、スクリーンショットの電子領収書を混ぜる。正解の項目を人が付けて `testset/` に置く(正解データは `testset/labels.json`)。

| 指標 | 合格ライン(提案値・未検証) |
|---|---|
| テキスト層ありPDF 1ページ | 1秒以内 |
| スキャン・写真1枚(OCRから抽出まで) | 3秒以内(最低ライン相当) |
| 日付・金額の正答率 | 95%以上(確認画面で直せる前提で、まず測る) |
| 支払先の正答率 | 90%以上 |
| ピークメモリ | 4GB以内 |
| インストール容量(モデル込み) | 2GB以内を目安 |

- 測定は、GPUを使わない設定・スレッド数6〜12で行う。Mac(Apple Silicon)は最低ラインより速いので基準にしない。
- 合格しない場合は、(a) ルールの拡充、(b) より小さい/別のOCR、(c) 機能の縮小、(d) 推奨スペックの引き上げ、の順に提案して**止まる**。

## データの保存と削除

- 保存場所: OSのアプリデータフォルダ内の、アプリ専用フォルダ(原本のコピー、SQLite、ログ)。
- 削除: 設定の「全データを削除」で、原本のコピーを含めてすべて消える。アンインストール時の扱いを画面に書く。
- 暗号化: 初版はアプリ内の暗号化を行わない。OS のディスク暗号化(BitLocker / FileVault)の案内を設定画面に載せる。SQLCipher の採用は「要確認」に書いて判断を待つ。
