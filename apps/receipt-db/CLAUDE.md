# 領収書DB（仮称） 開発ルール

このリポジトリは「領収書DB（仮称）」(slug: receipt-db)を作る場所です。作業の前に必ず SPEC.md を読んでください。

## 目的とスコープ

- 領収書や請求書のPDF・画像を取り込むと、日付・金額・支払先を読み取って検索できるデータベースに。ファイルはパソコンの外に出ません。
- 対象: 個人事業主・副業の方、領収書をクラウドAIに貼って整理していた方
- 1本あたり最大2週間で出せる大きさに保つ。SPEC.md の「スコープ」にない機能は足さない。思いついた案は SPEC.md の「見送り」に1行で書くだけにする。

## 守ること

1. **通信**: ユーザーのデータ(画像・音声・文章)を端末の外に出さない。通信してよいのは SPEC.md の「通信一覧」に載っているものだけ。新しい通信を足すときは、先に一覧へ追記して理由を書く。
2. **共通コア**: ライセンス検証・モデル管理・書き出しは `core/` を使う。自作しない。`core/` を直す必要が出たら、直さずに SPEC.md の「要確認」に書いて止まる(コアは全アプリで共有するため)。
   **決済・カート・税・ライセンス発行は実装しない。** 販売は外部の販売プラットフォーム(選定の経緯は `docs/sales-platforms.md`)に任せ、アプリ側は `core/` のライセンスクライアントだけを使う。
   対応OSは macOS(Apple Silicon)と Windows(x64)のみ。スマートフォン向けの実装は作らない。
3. **人が確認する画面**: AIの出力は必ず、保存・書き出しの前に利用者が確認・修正できる画面を通す。自動で確定しない。
4. **表現**: アプリ内の文言、販売ページの説明、LPは `checklists/copy-rules.md` に従う。「完全対応」「確実」「法的に問題なし」などの断定は使わない。
5. **品質**: ビルドとテストが通る状態でコミットする。1機能ごとにコミットし、SPEC.md のチェックボックスを更新する。

## 止まって確認すること(勝手に実行しない)

次のことは、実行せず SPEC.md の「要確認」に書いて、作業を止めてください。

- 価格の決定、販売プラットフォームでの商品登録、署名証明書の取得、配布ページへの公開
- 決済・ライセンス発行に当たるコードの追加(必要だと感じた場合も、理由を書いて止まる)
- アカウントの作成、証明書・鍵・トークンの生成や保存
- ユーザーデータを送信する通信の追加
- スコープの変更、共通コアの変更

## 進め方

1. SPEC.md の「技術選定」が未記入なら、まず候補と選んだ理由を書く(共通コアの方針 `core/README.md` に合わせる)。
2. スコープの上から順に実装する。各機能は「動く最小形 → 確認画面 → 書き出し」の順。
3. 完了したら `checklists/release.md` を上から確認し、できていない項目を SPEC.md の「要確認」に書き出す。

## 技術の前提と、テストデータの扱い

- 殻は Tauri 2(Rust)+ React + TypeScript + Vite を初期案とする。変える場合は、スパイクの結果と理由を SPEC.md の「技術選定」に書いてから。
- Rust 側のロジックにはテストを書く(`cargo test`)。`core/engine/` のテストは壊さない。
- **テストデータに、実在する他人の個人情報(名刺・領収書・録音)を使わない。** 架空のデータを自作するか、個人情報を伏せたものだけを `testset/` に置く。`testset/` は `.gitignore` に入れず、架空であることを `testset/README.md` に書く。
- 性能の測定は、GPUを使わない設定・スレッド数6〜12で行い、結果は `docs/spike-results.md` に表で残す。Mac(Apple Silicon)の結果は基準にしない。「近似」であることを書く。
- 依存ライブラリとモデルは、**商用利用できるライセンスか**を確認して `docs/licenses.md` に一覧にする(名前、バージョン、ライセンス、配布時に必要な表記)。確認できないものは使わず、「要確認」に書く。
