# スパイク結果(2026-10-03)

**先に読むこと**

- 測定環境は、クラウドの Linux 仮想マシン(x86_64、**4 vCPU**、メモリ 15GB、GPUなし)。基準の最低ライン(Core i5-12500 級、6コア12スレッド)より**コア数が少なく、機種も違う**ので、時間はすべて「近似」。Mac・Windows では**何も測っていない**(未実測)。
- テストセットは**架空の合成データ 50件**(`testset/`、同じフォントで描いた画像と、自作のPDF)。実際の紙・撮影・実在のレイアウトではない。**ここでの正答率は実データより高く出る。実データの精度は未実測。**
- ルール(`src-tauri/src/rules.rs`)は、OCR結果の失敗例を見たあとで直した(和暦の「令」の読み違い、`\` を円記号、「1, 080」の空白、「請求金额」の読み違い、合計の語が読めないときの代替)。**同じ50件で直して同じ50件で測っているので、数字は楽観的**(過学習の可能性)。直す前後の差は下の表に残した。
- 数値は捏造していない。測れなかったものは「未実測」と書く。

## 1. 結果の表(50件)

件数の分母は 50(テキスト層ありPDF 15 を含む。この15件は全エンジンで同じ結果)。支払先は「完全一致」と、括弧内は「1文字以内の違い」(確認画面で直せる程度)。

| 構成 | 日付 | 金額 | 税率 | 登録番号 | 支払先 | OCR時間(中央値/最大、画像35枚) |
|---|---|---|---|---|---|---|
| A. Tesseract 5.3.4 日本語(fast, 2.4MB) | 38 | 35 | 38 | 35 | 47 (49) | 0.26秒 / 0.57秒(`OMP_THREAD_LIMIT=1`) |
| B. Tesseract 日本語(best, 14MB) | 39 | 47 | 30 | 36 | 38 (40) | 0.53秒 / 0.97秒 |
| C. Tesseract fast + 2倍拡大 | 34 | 34 | 41 | 31 | 45 (49) | 0.47秒 / 1.19秒 |
| D. PP-OCRv4(中国語認識)・Python版 RapidOCR 1.4.4 | 50 | 50 | 50 | 50 | 15 (15) | 0.4〜2.8秒(スキャンPDF画像が最大) |
| E. 自作 Rust `PpOcr`(検出 v4 + 認識 v4 中国語) | 50 | 50 | 50 | 50 | 15 (15) | 約0.36秒 / 0.95秒 |
| F. 自作 Rust `PpOcr`(検出 v4 + 認識 日本語 v3 のみ) | 44 | 47 | 48 | 27 | 48 (50) | 0.27秒 / 0.85秒 |
| **G. 自作 Rust `PpOcr` 2モデル併用(日本語 v3 と中国語 v4 の両方で読み、数字は中国語、支払先は日本語)** | **50** | **50** | **50** | **50** | **48 (50)** | **2スレッド 0.62秒 / 1.43秒、4スレッド 1.05秒 / 1.78秒** |
| テキスト層ありPDF(Rust `pdf-extract`、15件) | 15/15 | 15/15 | 15/15 | 15/15 | 15/15 | 平均 0.002秒/ページ |

ルール修正の効果(D、直す前→後): 日付 42→50、金額 36→50。Tesseract A は 日付 38 のまま金額 23→35、登録番号 31→35。

読み取れなかった原因(実測で見えたこと):
- 中国語の認識モデル(v4)は**仮名と一部の漢字を落とす**(「有限会社かもめ園芸」→「有限会社芸」)。数字・英字・記号は正確。→ 支払先は 15/50(テキスト層のPDFだけ)。
- 日本語の認識モデル(v3)は、**「T」を「1」、「¥」を「半」、数字の1文字を読み違える**ことがある。登録番号は 27/50。
- Tesseract は数字の1文字落ち・入れ替えが多く(「T3730143821086」→「T1373914382108」)、薄い画像・傾いた画像で悪化する。「\」を円記号として返す。
- 併用(G)は、同じ検出結果を2つの認識モデルで読む。計算は認識の分だけ増えるが、1枚 約0.6〜1秒。

## 3. 測定中に見つけた注意点

- **スレッド数**: 4 vCPU の機械で `OMP_THREAD_LIMIT=4`(Tesseract)にすると、1枚 0.25秒が 25秒に悪化した(1〜2 でも 0.25秒)。ONNX Runtime でも 4スレッドが 2スレッドより遅かった(1.05秒 対 0.62秒)。スレッドの空回りとみられる。**最低ライン機(6コア12スレッド)で、スレッド数を 1・2・4・6 と変えて測るまで、既定値を決めない。**
- **画像のサイズ**: 検出は短辺が 736 未満なら 736 まで拡大する(これが時間の大半)。大きい画像は長辺 2000 に縮める。
- **傾き**: 検出結果の領域は、主成分で向きを求めて水平に切り出す(傾き ±6° の合成画像 5枚で、数字の項目は 5/5)。縦書きは領域の形で判定して横にして読む。**縦書きの実画像は未検証**(単体テストは合成の確率マップのみ)。
- **全文検索**: SQLite 3.53 の FTS5 `trigram` は、3文字以上の語(「ひまわり」「さくら書店」)は当たるが、**2文字の語(「書店」「文具」「会社」)は 0 件**。そこで、3文字未満の語だけ `LIKE` に切り替える(`core/engine/src/db.rs`、テストあり)。半角カナ「ﾋﾏﾜﾘ」は当たらないので、保存と検索の両方を NFKC でそろえる。
- **PDFのテキスト層**: PyMuPDF(AGPL。製品には使えない)の結果と、Rust の `pdf-extract`(MIT)の結果が 15/15 で一致。

## 4. 測れなかったこと・試さなかったこと(未実測)

| 項目 | 理由 |
|---|---|
| Mac(Apple Silicon)・Windows でのビルドと速度 | この環境は Linux のみ |
| OS標準OCR(macOS Vision、Windows の OCR)との精度・速度の比較 | 同上。OSごとに別のコードが要るので、手間でも ONNX 方式に劣る見込み(推測) |
| Core i5-12500 級(6コア12スレッド)での時間 | 実機なし。4 vCPU の仮想マシンでの近似のみ |
| 実際の領収書・レシート(感熱紙、撮影、影、手ブレ)での精度 | 実データを使わない方針。合成画像のみ |
| PP-OCRv5 の日本語認識、YomiToku、NDLOCR-Lite | 配布元(huggingface.co、modelscope.cn、paddleocr.bj.bcebos.com、github.com の本体と releases)への通信が、この環境の制限で失敗した(接続拒否・403)。YomiToku と NDLOCR-Lite は、ライセンスが商用同梱に使えるか未確認のため試していない |
| スキャンPDF(画像のみ)の画像化 | PDFium のバイナリが GitHub releases(通信制限)にあり未取得。この測定では PyMuPDF で画像にして OCR へ渡した(製品では使えない)。代替案は下の「提案」 |
| 日本語認識モデル(japan_PP-OCRv3)の公式配布元からの取得と検証 | 公式の配布元に届かず、npm の再配布パッケージ(`multilingual-purejs-ocr` 1.0.1)から取得した。出所とライセンス表記の確認が必要(`docs/licenses.md`) |
| macOS / Windows 用の onnxruntime 共有ライブラリの取得と読み込み | Linux 版(PyPI の onnxruntime 1.30.0 に入っているもの)でのみ確認 |
| 1ページ目以外、複数ページPDF | 測っていない(1ページのみ) |
| 100件一括処理の10分以内(受け入れ基準) | 未実施(取り込みの実装前) |

## 5. 選定と、報告時の提案

- **OCR: ONNX Runtime 上の PP-OCR(`core/engine/src/ocr/ppocr.rs`、検出 + 認識の2モデル併用)を採用案とする。** 理由は、(1) OSごとのコードが要らない(Mac・Windows で同じ実装)、(2) 実測で、数字と日本語の両方が合成データで合格ラインに届いた、(3) 手間: 画像処理は `image` クレートだけで書け、Tesseract のような外部の実行ファイルの同梱が要らない、(4) 速度と容量が余裕(約55MB)、(5) ライセンスが商用向き。
- **Tesseract(`TesseractOcr`)は予備**として core に残す(実行ファイルを同梱できれば使える)。単独では数字の精度が足りない(A〜C)。
- **提案(PDF)**: 画像のみのPDFは、(a) PDFium(BSD、`pdfium-render`)の共有ライブラリを配布元から取得して同梱する、または (b) まずスキャナー出力に多い「1ページ1枚のJPEG」を `lopdf`(MIT)で取り出して OCR に渡す、の順に試す。(a) の取得に GitHub releases への通信が要るので、ネットワーク制限が外れた環境か、利用者側の手動配置が必要。
- **提案(精度)**: 実際の領収書(個人情報を伏せたもの)20〜30件の提供を受けて、同じ手順で再測定する。
- 再現手順: `testset/gen_testset.py` で生成 → `tools/spike/bench_ocr.py`(Python の候補比較)、`core/engine/examples/ocr_dump.rs`(Rust の `PpOcr` / `TesseractOcr`)でテキストを出す → `src-tauri/src/bin/spike_eval.rs` で labels.json と突き合わせる。
