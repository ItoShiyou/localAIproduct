# スパイク結果(ノイズ除去と文字起こし)

実施日: 2026-10-03 ／ 状態: ノイズ除去は実測。**文字起こしは 2026-10-04 に Mac(M2)で実測(下の 4・5)。**

## 測定環境と、結果の読み方(必読)

- クラウドの Linux(仮想 4 コア、メモリ 16GB、GPU なし)。**スレッド数は 4**(規定の 6〜12 に届かない。最低ライン機 Core i5-12500 より遅い側の環境)。Mac / Windows の実機では測っていない。結果はすべて「近似」。
- 同じ機械で他の作業が動いており(負荷平均 5〜8)、時間は揺れる。DFN3 は 1 回目(競合あり)と 2 回目(競合が小さい)の両方を載せる。
- テストセットは**架空の台本の合成音声 + 合成雑音**(`testset/README.md`)。本数は 6 本・計約 20 分で、SPEC の「5〜10本・各5〜30分」より少ない。実際の会話音声ではないので、品質の数値は参考値。
- 再現: `spike/make_testset.py`、`spike/bench_denoise.py`、`spike/bench_asr.py`。

## 1. ノイズ除去(実測)

候補: RNNoise(pyrnnoise 0.4.5 経由)、DeepFilterNet3(DFN3、PyTorch 版・CPU)。いずれも 16kHz 入力を内部で 48kHz に変換して処理。

| 録音(長さ) | モデル | 処理時間 / 再生時間(RTF) | 備考 |
|---|---|---|---|
| t06 長尺(661秒) | RNNoise | 43.3秒(0.066) | 合格ライン(0.5 以下)を満たす |
| t06 長尺(661秒) | DFN3 | 25.1秒(0.038)。1 回目 25.4秒(0.038) | 同上 |
| 165秒の4本(t01〜t04) | RNNoise | 約 10〜11秒(0.06〜0.07) | 安定 |
| 165秒の4本(t01〜t04) | DFN3 | 2 回目: 約 5.6秒(0.033〜0.035)。1 回目: 5.0〜88.2秒(0.03〜0.53) | 1 回目は他の作業との競合で最大 0.53 に悪化(CPU 時間も 17→263秒に増えた)。競合下では合格線(0.5)を超えた例がある |

| 品質の目安(SI-SDR、基準の無雑音音声に対して。大きいほど良い) | 入力 | RNNoise | DFN3 |
|---|---|---|---|
| t02 エアコン(SNR 5 dB) | 5.0 dB | 11.6 dB | 12.5 dB |
| t03 キーボード(SNR 5 dB) | 5.0 dB | 15.8 dB | 14.6 dB |

- SI-SDR は信号の近さの指標で、**聞き取りやすさ・文字起こしの誤り率とは別物**。合成音声と合成雑音での値であり、実会議音声では変わる。t04(遠いマイク)と t05(同時発話)は基準が一致しないため SI-SDR を出していない。
- **ノイズ除去が文字起こしの誤り率を上げるか下げるかは未測定**(文字起こしを測れていないため)。競合調査にあるとおり、除去が逆に精度を下げる場合もあるため、オン/オフ式にする SPEC の方針は妥当。除去後の音声を聞いての主観評価も、この環境ではできていない。
- ピークメモリ(RSS、Python と PyTorch を含む。全体を一括処理した値): RNNoise 約 0.74〜1.2GB(661秒で 1.16GB)、DFN3 165秒で約 2.2GB、**661秒で約 6.5GB(合格ライン 4GB を超える)**。製品では区間(数十秒)ごとの処理にすれば抑えられる見込みだが、**区間処理でのピークは未測定**。ONNX / Rust 実装でのメモリも未測定。
- 発見: DFN3 に**完全な無音(サンプル値が 0 だけ)が続く入力を渡すと、極端に遅くなった**(165秒の入力が 500秒以上かかり打ち切り)。微小ノイズ(振幅 1e-4)を足すと解消。製品では、無音区間を飛ばす・微小ノイズを加えるなどの対策が要る。
- モデルのサイズ: DFN3 の ONNX 版アーカイブ 約 8MB(取得時のファイルサイズ)。RNNoise はライブラリ内蔵(pyrnnoise の wheel 全体で約 13MB)。インストール容量 2GB の枠には、どちらも余裕で入る。

### ノイズ除去の暫定の見立て

- どちらも速度の合格ライン(再生時間の半分以内)は満たした(DFN3 の競合下の一例を除く)。
- 軽さ・安定は RNNoise、雑音の種類への強さは DFN3 に見込みがあるが、**実会議音声と聞き取り評価が無いため、優劣は決めない**。初版の案: RNNoise を既定とし、DFN3 を選べる形を検討(要確認)。

## 3. 結論と、止まる理由

- ノイズ除去: 速度は合格ラインの範囲。メモリは区間処理が前提(未検証)。品質と文字起こしへの影響は未測定。
- 文字起こし: **今回の環境では測れなかった**。SPEC の手順(合格ラインに届かない場合は提案して止まる)の「届かない」ではなく「測れていない」状態。HANDOFF と KICKOFF の方針どおり、**実装には入らずここで止まる**。
- 次に必要なこと: ①モデルを取得できる環境での文字起こし 3 候補の実測、②実機(Mac / Windows、できれば i5-12500 級)での確認、③実会議に近い音声での評価、④ライセンスの「要確認」の解消。

## 5. 製品の実装での実測(Mac M2、2026-10-04。`src-tauri/tests/real_asr.rs`)

アプリと同じ処理(`pipeline`: 16kHz への変換 → 30 秒以内の区間に分割 → ノイズ除去(オン/オフ)→ whisper.cpp で文字起こし)を通した値。モデルは `ggml-large-v3-turbo-q5_0.bin`(574MB)、6スレッド、GPU 不使用、greedy。ほかの作業は止めて測った。

| 録音 | ノイズ除去なし CER | ノイズ除去あり CER | 処理時間/再生時間(なし / あり) |
|---|---|---|---|
| t01 雑音なし(165秒) | 4.10% | 4.25% | 0.26 / 0.29 |
| t02 エアコン(SNR 5dB) | 4.25% | **3.66%** | 0.28 / 0.32 |
| t03 キーボード(SNR 5dB) | 6.15% | **4.10%** | 0.34 / 0.32 |
| t04 遠いマイク | **3.95%** | 6.30% | 0.30 / 0.39 |
| t05 同時発話(56秒) | 13.2% | 11.2% | 0.39 / 0.29 |

- ピークメモリ(テストのプロセス全体、モデル読み込み込み): **約 0.97GB**(合格ライン 4GB 以内)。モデル容量 574MB(インストール 2GB の目安以内)。
- 速度: M2・6スレッドで再生時間の約 0.26〜0.39 倍。**最低ライン機(i5-12500、GPU なし)では未実測**。M2 より遅くなる見込みだが、「再生時間と同程度以内」の目標に対しては余裕がある可能性が高い(推測であり、Windows 機で確認が必要)。
- **ノイズ除去は、エアコン・キーボード雑音では誤りを減らし、遠いマイク(残響)では増やした。** SPEC の方針どおりオン/オフ式にし、設定画面に「結果が良くないときはオフにして取り込み直す」案内を入れた。既定はオンのまま(実会議音声での評価がないため、既定値は要確認)。
- ノイズ除去単体: nnnoiseless(RNNoise の Rust 移植)で、t02 先頭60秒の SI-SDR が 5.1 → 10.6 dB(スパイクの pyrnnoise 11.6 dB とほぼ同等)。実装時に RNNoise の出力が 1 フレーム(10ms)遅れることを見つけて補正した(補正前は -28 dB)。
- アプリでの実文字起こしは `docs/ui/mac-real-transcription.png`(t02 を取り込み、起動時の自動再開で処理)。
- 制約: 合成音声(話速・抑揚が一定、言い淀みなし)。実会議の録音、1〜2時間の長尺、Windows 機では未確認。

## 7. 話者の自動判別(Mac M2、2026-10-04。`src-tauri/tests/real_diarize.rs`)

評価用の音声: `spike/make_diarize_testset.py` で、macOS の `say`(Kyoko・Eddy・Grandpa・Flo の4つの声)により合成した**架空の4人の打ち合わせ**(16 発話、80.6 秒、発話の間に 0.6 秒の無音)。Apple の音声の再配布条件が未確認のため、音声は Git に入れず、生成の手順だけを置く。

| 方式 | 推定した人数 | 文ごとの正答(純度) | 備考 |
|---|---|---|---|
| 文字起こしの文ごとに特徴を求めてまとめる(最初の案) | 4 | 0.67 | Whisper の文の時刻がずれ、隣の話者の声が混ざる |
| **声のある所を間で区切った 3 秒以下の窓ごとに特徴を求め、平均連結でまとめ、小さなまとまりを寄せ、文は窓の多数決**(採用) | **4(自動)** | **1.00(21/21)** | 人数を 4 と指定しても 1.00 |

- 声の特徴: WeSpeaker ResNet34-LM(ONNX、CC BY 4.0)。前処理の fbank は Rust で実装し、kaldi-native-fbank と比べて埋め込みのコサイン類似度 0.9993。
- 処理時間: 80 秒の音声で、文字起こし込み 22 秒(話者の判別の部分は 1 秒程度)。
- 同梱した .app(onnxruntime 1.30.0 と WeSpeaker を同梱、環境変数なし)でも、既存のデータベースを新しい形に更新したうえで、同じ録音から4人を判別できた。
- **限界**: 合成音声(声がはっきり違い、話者の重なりが無く、間がある)での結果。実際の会議(声の似た人、重なる発話、相づち、遠いマイク)では精度が下がる見込み。人数の指定と、名前の一括変更・判別し直し・手での付け替えで補う前提。


## 8. 録音中の仮の文字(Mac M2、2026-10-04)

録音中は速さを優先し、止めたあと正確なモデルで置き換える(利用者の方針: 10〜20 秒遅れでよく、録音中は低精度でよい)。

| モデル(whisper.cpp、4スレッド) | 容量 | t01 雑音なし CER | t02 エアコン CER | 処理時間/再生時間 |
|---|---|---|---|---|
| **small q5_1(録音中に採用)** | 190MB | 6.2% | 8.5% | 0.06 |
| base q5_1 | 60MB | 11.0% | 17.0% | 0.02 |
| (参考)large-v3-turbo q5_0(正確な文字起こし、6スレッド) | 574MB | 4.1% | 4.3% | 0.26 |

- 実際の速さで 0.5 秒ずつ渡す試験(`tests/real_live.rs`、架空の4人の会議 80.6 秒): small で待ちの区間は最大 1、止めてから仮の文字が出そろうまで 0.8 秒。large-v3-turbo でも待ちは最大 2 で追いついたが、CPU の負担が約4倍。
- 区切り: 声の切れ目(0.6 秒以上の無音)、4 秒未満は切らない、25 秒で必ず切る。
- 画面のマイク取り込み(getUserMedia → AudioWorklet → 16kHz → 0.5 秒ごとに送る)は、Chromium の疑似マイクで e2e を通した。**実機(Mac の WKWebView とマイク)での録音は未確認。**

### 12b. Windows の文字起こしが遅かった原因と修正(GitHub Actions の windows-latest、2026-10-05)

上の「RTF 4.5」は、**whisper.cpp(ggml)が最適化なし(MSVC の /Od 相当)でビルドされていたため**だった。CPU の命令(AVX2 など)が無効だったわけではない。値はいずれも共有のホスト型ランナー(4 論理 CPU)での測定で、**実機(i5-12500 など)の速さではない**。

- **切り分け**: (1) `whisper_print_system_info()` を `real_asr` テストに出させた結果は `AVX = 1 | AVX2 = 1 | F16C = 1 | FMA = 1`(命令は有効)。(2) スレッド数 1・2・4 で処理時間がほぼ反比例した(1: 458〜868 秒、2: 253〜375 秒、4: 191〜295 秒。同じ構成で繰り返してもばらつきが大きい)ので、スレッドが使われていないわけではない。(3) whisper-rs-sys が生成した ggml-cpu の Visual Studio プロジェクトを見ると、Release の `<Optimization>` が空で、`CMakeCache.txt` の `CMAKE_C_FLAGS_RELEASE` が `-nologo -MD -Brepro -W0` だけ。cmake クレートがこの変数を上書きし、MSVC の既定(`/O2 /Ob2 /DNDEBUG`)が消えていた。cargo の profile は release(`cargo test --release`)で、Rust 側の最適化の問題ではない。
- **修正**: 環境変数 `CMAKE_C_FLAGS_RELEASE` / `CMAKE_CXX_FLAGS_RELEASE` を `-O2 -Ob2 -DNDEBUG` にする(whisper-rs-sys と llama-cpp-sys-2 は `CMAKE_` で始まる環境変数をそのまま CMake に渡す)。`/O2` と書くと Git Bash(MSYS)がパスとして書き換えて壊れるので、ハイフンで書く。`.github/workflows/minutes-windows.yml` のワークフロー全体の env と、`tools/build_summarizer.sh`(Windows ターゲットのときだけ)に入れた。**Mac のビルドには影響しない**(Windows のターゲット・CI の env だけ)。ローカルの Windows で `cargo build` するときも同じ環境変数が要る。
- **別の問題も見つけた(CPU 命令のビルド元依存)**: whisper.cpp は MSVC で `GGML_NATIVE` が既定で ON になり、**ビルドした機械の CPU を調べて命令を決める**。CI のランナーは日によって機種が違い(AMD EPYC 7763、Intel Xeon 6973P-C、Intel Xeon Platinum 8573C を確認)、後者の 2 つで `AVX512 = 1` のビルドができた。AVX-512 のある機種でビルドした配布物は、AVX-512 の無い CPU(Intel 第 12 世代の i5-12500 など)で不正な命令で落ちるおそれがある(落ちることまでは未確認)。そこで `.github/scripts/ggml-x64-baseline.cmake` を `CMAKE_PROJECT_INCLUDE` で読ませ、`GGML_NATIVE=OFF`、AVX2・FMA・F16C・BMI2 を ON、AVX-512 を OFF に固定した。
- **CPU の基準(決定)**: **AVX2 + FMA + F16C + BMI2(Intel Haswell・2013 年以降、AMD Zen 以降)**。i5-12500(最低ライン機)は満たす。**これより古い CPU(2013 年より前の Intel、AVX2 の無い Celeron/Pentium の一部など)では起動はしても文字起こしで落ちる**ため、動作環境に「2013 年以降の CPU(AVX2 対応)」と書く必要がある(要確認: 起動時に AVX2 が無いことを検知して案内を出す実装は未)。ggml の実行時の命令選択(`GGML_CPU_ALL_VARIANTS`、`GGML_BACKEND_DL`)は、whisper-rs 0.15.1 の build.rs が対応しておらず(共有ライブラリ化が要る)、使っていない。
- **測定(small = 同梱の ggml-small-q5_1、スレッド 4、t05_overlap 55.7 秒、ノイズ除去なし、release ビルド)**:

| ランナーの CPU | 修正前(最適化なし) | 修正後 |
|---|---|---|
| AMD EPYC 7763(同じジョブ内で前後を測定) | 245.9 秒(RTF 4.41) | 21.2 秒(RTF 0.38) |
| Intel Xeon 6973P-C(同じジョブ内で前後を測定) | 143.3 秒(RTF 2.57) | 19.5 秒(RTF 0.35) |
